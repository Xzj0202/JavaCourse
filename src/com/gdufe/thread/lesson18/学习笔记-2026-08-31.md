# 学习笔记 · 2026-08-31（AtomicInteger / CAS / 竞态三部曲收官）

## 1. 竞态条件三部曲总表

| 工具 | 管什么 | 不管什么 |
|---|---|---|
| synchronized | **排队**：同一把对象锁，一次一个线程进临界区 | 粒度太大就串行化，性能损失 |
| volatile | **传话**：写立刻刷主内存、读强制看主内存 | **原子性**（count++ 照样丢更新） |
| AtomicInteger | **动作**：单个操作（incrementAndGet 等）不可切 | **组合操作**（先查后改，仍需锁） |

共享标志位铁律：要么 volatile，要么全程锁保护，二选一，裸奔必出事。

## 2. CAS 原理（为什么不用锁也不丢）

`incrementAndGet()` 内部（假设 count 当前 = 5）：

| 步 | 动作 |
|---|---|
| 1 | 读主内存当前值 v = 5 |
| 2 | 算出新值 6 |
| 3 | **compareAndSet(5, 6)**：一条硬件原子指令——「现在还是 5 吗？是 → 换成 6；不是 → 什么都不做」 |
| 4 | 失败 → 回到第 1 步重试（**自旋**），直到成功 |

双线程抢 5 的推演：

```
A: CAS(5→6) 成功 → count = 6
B: CAS(5→6) 失败（期望 5，实际已是 6）→ 重读 → CAS(6→7) 成功
```

关键：第 3 步「比较 + 替换」是 CPU 层面一条指令（x86 的 cmpxchg），线程切换插不进去——「读-加-写」三步里最危险的「检查-写入」被压成了一个不可分割的动作。

## 3. 实测数据（今天的实验）

- VolatileRace（`volatile int count; count++`，2 × 10000）：**16518 / 11485 / 16429** ——丢更新实锤，volatile 不保原子性
- AtomicRace（`AtomicInteger`，2 × 20000）：**40000 × 6 连跑**，一次不丢

## 4. API 要点

- `count.get()` / `count.set(n)` / `count.incrementAndGet()` / `count.getAndIncrement()`
- **incrementAndGet = `++count`**（返回加完的新值）；**getAndIncrement = `count++`**（返回加之前的旧值）——面试官爱问
- AtomicInteger 不能当 int 用：`int x = count + 1` 编译不过
- 自旋代价：竞争激烈时大家频繁失败重试、烧 CPU（但不排队阻塞）；JDK 8 有 LongAdder 分散热点，知道名字即可
- 组合操作不原子：`if (count.get() < 10) count.incrementAndGet()` 是先查后改两个操作的组合，中间照样被切——该上锁还是上锁
